### One local edit to the BalatroBot mod (2026-09-13)

**One file** of the installed mod is no longer stock:

| Path | Change |
| --- | --- |
| `~/Library/Application Support/Balatro/Mods/balatrobot/src/lua/utils/gamestate.lua` | +~120 lines, purely additive |
| `vendor/balatrobot/src/lua/utils/gamestate.lua` | the same edit, so the two copies stay byte-identical |

It adds two optional output fields and changes nothing that already existed:

* **`card.geometry`** on every extracted card: where that card is on screen
  *right now*, in LOVE pixels: `{rect: {x, y, w, h, r}, vt, t, room, unit,
  moving}`. Balatro is LÖVE, and every card is a `Moveable` with two transforms
  in game units: `T` is the target and `VT` is the **visible** one, which eases
  toward `T` over a few frames. A card mid-deal, mid-discard or being raised is
  *drawn* at `VT` (`engine/node.lua:draw_boundingrect` takes `self.VT or
  self.T`), so `rect` is computed from `VT` by the same arithmetic
  `Node:put_focused_cursor` uses:
  `pixel = (VT.<x|y> + G.ROOM.T.<x|y>) * (G.TILESCALE * G.TILESIZE)`.
  The raw `vt`, `t`, `room` and `unit` values are reported alongside it so a
  consumer can re-derive or re-fit that mapping without another Lua change.
* **`state.screen`** at the top level: `tilesize`, `tilescale`, `unit`, the
  room rect, and LÖVE's `getDimensions()` / `getPixelDimensions()` /
  `getDPIScale()`, because the overlay is positioned in window **points** and
  the rects above are in **pixels**, which differ by the Retina backing scale.

Both are wrapped in `pcall` and both are optional: if the game's internals ever
move, the field is absent and every existing endpoint behaves exactly as
before. Nothing was removed, renamed or reordered, so the OpenRPC schema and
every existing client keep working. The Python side treats a missing field as
"fall back to the fitted static fan" (`flybalatro/realgame/overlay.py`,
`aligned_rects`).

**A new Lua file is only loaded when the game starts**, so this edit takes
effect on the next launch of Balatro and not before.

To revert just this edit, leaving the rest of the install alone:


**What the install actually looks like** (checked 2026-09-13):

| Check | Value |
| --- | --- |
| `Balatro.love` → `version.jkr` | `1.0.1o-FULL` (BalatroBot needs ≥ 1.0.1) |
| `Info.plist` `CFBundleShortVersionString` | `11.5`, which is **LÖVE 11.5**, not a Balatro version |
| `Info.plist` `CFBundleIdentifier` / `CFBundleExecutable` | `com.Balatro.localthunk` / `love` |
| binary | `Balatro.app/Contents/MacOS/love`, Mach-O **universal** (x86_64 + arm64) |
| `codesign -dvvv` on `love` | `flags=0x20002(adhoc,linker-signed)`, `Signature=adhoc`, `Sealed Resources=none`, no entitlements |
| quarantine | none, on the game or the dylib (only `com.apple.provenance`) |

The three things that would have blocked `DYLD_INSERT_LIBRARIES` are all
absent: **no hardened runtime** (no `runtime` in the flags), **no
library-validation entitlement** (`codesign -d --entitlements -` returns
nothing at all), and no quarantine. So the plain copy was enough.

**No `codesign --force --deep --sign -` was needed and none was run.** The
game's signature is exactly as Steam shipped it. Do not re-sign pre-emptively:
an ad-hoc re-sign of a universal binary is a change to a file Steam owns and
will be silently reverted by the next update anyway.

The `xattr -d` is a no-op here (a `curl` download sets `com.apple.provenance`,
not `com.apple.quarantine`) but it is harmless and costs nothing to keep.

`run_lovely_macos.sh` is **not** needed: `balatrobot serve` sets
`DYLD_INSERT_LIBRARIES` itself and execs the LÖVE binary directly
(`vendor/balatrobot/src/balatrobot/platforms/macos.py`). Copy it only if you
want to launch the game modded but without the bot.

Steam does **not** need to be running: the launcher bypasses it, which is
deliberate: `docs/cli.md` notes you cannot launch through Steam on macOS due
to a Steam client bug.

### If injection fails — diagnose in this order

`DYLD_INSERT_LIBRARIES` is ignored for binaries with the hardened runtime and
library validation, which is the most likely failure on macOS 26.

```bash
BAL="$HOME/Library/Application Support/Steam/steamapps/common/Balatro"
LOVE="$BAL/Balatro.app/Contents/MacOS/love"

file "$LOVE"                              # must be arm64 (or use the x86_64 tarball)
codesign -dvvv "$LOVE" 2>&1 | grep -i flags   # look for "runtime" = hardened
codesign -d --entitlements - "$LOVE" 2>&1 | grep -i library-validation
```

* **Hardened runtime with library validation on** -> re-sign ad hoc, which
  drops the restriction:
  ```bash
  codesign --force --deep --sign - "$BAL/Balatro.app"
  ```
* **Gatekeeper quarantine on the dylib** -> the `xattr -d` above. A
  `curl` download does not set `com.apple.quarantine` (the staged copy has only
  `com.apple.provenance`), so this is unlikely.
* **Arch mismatch** -> an x86_64 LÖVE under Rosetta needs
  `lovely-x86_64-apple-darwin.tar.gz` instead.
* **SIP** does not strip `DYLD_*` for ordinary user apps, only for
  system/restricted binaries, so it is not the likely cause here.
* Mod-loading problems that are *not* injection failures show up in
  `logs/{timestamp}/{port}.log` from `serve`, and in Steamodded's in-game mod
  list.

## 4. Launch the modded game, then run the fly

**The exact sequence that worked on 2026-09-13**, from a cold machine with
Steam *not* running:

```bash
# 1. place the dylib (section 3)
BAL="$HOME/Library/Application Support/Steam/steamapps/common/Balatro"
cp "$REPO/vendor/lovely/liblovely.dylib" "$BAL/"

# 2. the game, demo-paced, logging where the project can read it
export PATH="$HOME/.local/bin:$PATH"
uvx --from "$REPO/vendor/balatrobot" balatrobot serve \
    --gamespeed 1 --animation-fps 60 --no-reduced-motion \
    --logs-path "$REPO/outputs/realgame/logs"

# 3a. the fly, frozen v3 readout (the original)
cd "$REPO" && source .venv/bin/activate
python -m flybalatro.realgame.play --ante-end 1 --pause 1.5

# 3b. or the LEARNING fly: no trained action readout at all, and the
#     KC -> MBON synapses change while it plays. Naive by default.
python -m flybalatro.realgame.play --plastic --ante-end 1 --pause 1.5
```

`--plastic` is `flybalatro/realgame/plastic.py`. It swaps the readout for the
fly from `RESULTS.md` "Plasticity v2": the decision is
`mean rate(approach MBONs) - mean rate(avoid MBONs) + bias` over the fly's own
mushroom-body output neurons, with **nothing fitted to actions, labels or
outcomes**, and the chips the game pays deliver dopamine that depresses the
eligible Kenyon-cell → MBON synapses. The operating point (the 4,064 per-KC
homeostatic thresholds, `apl_kc_only`, `apl_mbon_scale`, and the two calibrated
scalars `bias` and `temperature`) is **loaded** from `outputs/plast2/`, never
refitted, so a real-game run and the headless runs in `RESULTS.md` are the same
fly. Useful flags:

| flag | what |
| --- | --- |
| `--warm-start` | start from `outputs/plast2/weights_real_eta0.05_s0.npz` instead of naive |
| `--no-learning` | the control: same decisions, dopamine computed and logged, never delivered |
| `--eta 0.05` | reward learning rate; the punishment rate is the calibrated 3.81× of it |
| `--save-weights PATH` | where the learned weights go (default `<out-dir>/weights.npz`) |
| `--max-hands N` | stop after N hands |

**With no game running**, the same loop can be exercised against a scripted
Balatro-shaped server that deals real cards and scores them with
`flybalatro/hands.py`:

```bash
python -m scripts.realgame_plastic_offline --hands 40                 # learning
python -m scripts.realgame_plastic_offline --hands 40 --no-learning   # the control
```

Everything but the game is the real thing there: the real client over real
HTTP, the real adapter, the real connectome at the real operating point, the
real loop. It is evidence that the loop closes, **not** evidence about how well
the fly plays Balatro; see the script's own docstring.

### The two seams that only the real game exposes

Both were found by running it, both are fixed in `adapter.py`, and both are
now pinned by tests.

**1. Lua cannot distinguish an empty object from an empty array.** A base
playing card arrives as `"modifier": [], "state": []`, where the schema says
object. `_obj` raised `ValueError: hand.cards[0].modifier: expected an object,
got list` on the very first hand. `_obj` now reads an *empty* list as `{}`; a
non-empty list is still an error, because that would be real data in an
unreadable shape.

**2. `pylatro` has no deselect, and the adapter was offering one.** This is
the one that matters. The mask allowed `select_card[i]` for an
already-selected slot so it could be toggled off. `pylatro` does not:

```python
>>> e = BalatroEnv(); e.reset(seed=100000); e.step(select_blind)
>>> e.step(1)      # select_card[1] -> ok
>>> e.step(1)      # select_card[1] again
IllegalActionError: action 1 (select_card[1]) is masked;
                    legal indices are [0, 2, 3, 4, 5, 6, 7, 70, 71]
```

So the adapter was handing the readout a strictly larger action space than it
was trained and evaluated on, and the v3 readout walked straight into the
extra action: **select slot 0, deselect slot 0, select slot 0, …** for 200+
decisions without ever playing a card.

This was not the readout being weak. `outputs/bc3/eval.json` records
`truncated_fraction: 0.0` for `real_alpn_kc_dn/mlp` over 400 headless
episodes; it never runs out of steps there, because the deselect action does
not exist there. The mask was wrong.

Two hypotheses were tested and rejected before the real one was found, which
is worth recording so nobody re-tests them:

* *The real game sorts the hand rank-descending and `pylatro` does not, so the
  positional encoding is off-manifold.* True as an observation (`pylatro`
  returns draw order, `[(4,3),(12,3),(3,3),(0,2),…]`), but **not** the cause:
  replaying the stuck hand under the game's sorted order, an id-hash
  permutation, and four random permutations produced the identical 2-cycle in
  all six. After the mask fix, all six reach a `discard`. Hand order is
  harmless.
* *`drive_bits` takes the wrong 32 of the 315 bits under `glomerular32`.* No:
  the relay block is the **leading** 32 bits (`flybalatro/glomerular.py`
  docstring, `relay_bits`), so `bits[:32]` is right.

### Screenshots and screen recording

Both work on this machine. The API route is the better one:

* **`screenshot` (API)**: writes wherever you point it. `screenshot.lua` uses
  `nativefs.write` on the raw path, so an absolute path outside the LÖVE save
  directory is honoured, which is not true of plain `love.filesystem`. Needs no
  window id, no focus and no screen-recording permission, and captures the game
  canvas only.
* **`screencapture -x` / `screencapture -v -V 28`**: both succeeded, so this
  machine has already granted screen recording. The clip is the whole desktop
  (~164 MB for 28 s at retina), not just the game window.

**One thing to know before you frame a shot: the fly's selection is virtual.**
The API has no card-selection endpoint, so the adapter carries the selection
itself and submits the indices at `play`/`discard` time. The cards are
therefore **never highlighted on screen**, no matter how many `select_card`
decisions the fly has made. A screenshot taken "mid-selection" shows an
untouched hand.

So capture on state, not on selection. `outputs/realgame/latest.json` is
already the right trigger; the moments that read as evidence are:

| Moment | Predicate | What it shows |
| --- | --- | --- |
| scoring | `SELECTING_HAND` and `round.chips > 0` | Round score climbing, hands/discards burnt down |
| round eval | `state == "ROUND_EVAL"` | the blind beaten, the payout |
| shop | `state == "SHOP"` | the fly between blinds |

Captured for this run: `outputs/realgame/balatro_fly.png` (Small Blind, round
score 292/300, 1 hand and 2 discards left), plus `balatro_fly_round_eval.png`,
`balatro_fly_shop.png`, `balatro_fly_firsthand.png` and the 28 s clip
`balatro_fly.mov`.

```bash
curl -s -X POST http://127.0.0.1:12346 -H "Content-Type: application/json" \
```

## 5. What the Python side does

`flybalatro/realgame/client.py`: stdlib JSON-RPC 2.0 client. Method names
mirror `docs/api.md` exactly (`buy`, `sell`, `pack`, `rearrange`, `use`, `play`,
…); the RPC method `set` is spelled `set_` because a method named `set` reads as
the builtin. The "exactly one of these keys" methods also have unambiguous
wrappers (`buy_card`, `sell_joker`, `pack_skip`, `rearrange_hand`, …) that
delegate. Maps the mod's four error names (`INTERNAL_ERROR`, `BAD_REQUEST`,
`INVALID_STATE`, `NOT_ALLOWED`) onto `BalatroBotError`, and transport failures
onto `TransportError`.

One trap in the API itself: **`use` takes its hand targets as `cards`, but
`pack` takes them as `targets`.** `pack` is also absent from
`src/lua/utils/openrpc.json`, so `src/lua/endpoints/pack.lua` is the source of
truth for it. Both spellings are pinned by tests.

`flybalatro/realgame/adapter.py`: `build_state()` turns a `gamestate` payload
into a duck-typed stand-in that `flybalatro.features.encode()` accepts
unchanged; `legality_mask()` produces the 109-wide mask with
`mask_noop_actions=True` semantics; `plan_action()` maps an action index onto
the BalatroBot call.

`flybalatro/realgame/play.py`: the loop, the readout loader (same npz layout
as `scripts/bc_train.py`'s `export_numpy`), and the logger.

### Two things worth knowing

**Selection is virtual.** The API has no card-selection endpoint: `play` and
`discard` take the hand indices to act on. pylatro instead has the agent toggle
`select_card[i]` and then issue a bare `play`. To keep one action space across
both, the adapter carries the fly's selection itself and submits it at
play/discard time. The game's own `card.state.highlight` is only ever read (to
seed a selection), never written, because nothing in the API can set it.

**`features.encode` reads only part of the state.** Only `available`,
`selected` (each card's `rank_index`, `suit_index`, `id`), `plays`, `discards`,
`score`, `required_score`, `money`, `stage.int()` and `len(jokers)`. It does
*not* read the deck, discard pile, enhancements, round or ante, so those are
carried on the state object for logging only and cannot change a bit.

### Field mapping

| pylatro / features | BalatroBot `gamestate` |
| --- | --- |
| `available` | `hand.cards[]` (game's display order) |
| `selected` | virtual, resolved from `selected_indices` |
| `plays` | `round.hands_left` |
| `discards` | `round.discards_left` |
| `score` | `round.chips` |
| `required_score` | `blinds.*.score` where `status == "CURRENT"`, else `"SELECT"` |
| `money` | `money` |
| `jokers` | `jokers.cards[]` |
| `card.rank_index` | `value.rank` `"2".."9","T","J","Q","K","A"` -> 0..12 |
| `card.suit_index` | `value.suit` `"S","C","H","D"` -> 0,1,2,3 |
| `card.id` | `id` (the game's `sort_id`) |

### Stage mapping

| BalatroBot `state` | `Stage.int()` |
| --- | --- |
| `BLIND_SELECT` | 0 `pre_blind` |
| `SELECTING_HAND`, `HAND_PLAYED`, `DRAW_TO_HAND`, `NEW_ROUND` | 1/2/3 by current blind `SMALL`/`BIG`/`BOSS` |
| `ROUND_EVAL` | 4 `post_blind` |
| `SHOP` | 5 `shop` |
| `GAME_OVER` | 6 `end_win` if `won` else 7 `end_lose` |
| `PLAY_TAROT` | 8 `tarot_hand` |
| `*_PACK`, `SMODS_BOOSTER_OPENED` | 10 `pack_open` |
| `MENU`, `TUTORIAL`, `SPLASH`, `SANDBOX`, `DEMO_CTA`, `UNKNOWN` | raises `UnmappableStateError` |

Nothing maps to 9 (`spectral_hand`): BalatroBot exposes spectral targeting
through `SPECTRAL_PACK`, a pack-open state.

### Actions with no BalatroBot equivalent

Always masked, and `plan_action` refuses them:

* `move_card_left/right` (24-69) and `sort_hand` (105, 106): masked anyway
  under `mask_noop_actions=True`; reordering never changes what a hand scores.
* `apply_tarot` (89) and `apply_spectral` (108): pylatro staging steps for a
  targeting flow BalatroBot performs atomically inside `use` / `pack`.

`buy_joker[i]` etc. are per-category slots in pylatro but a single array in
BalatroBot, so `buy_joker[1]` resolves to "the second JOKER in `shop.cards`",
whatever index that is.

### Policy modes, printed at startup

| Mode | Input to the readout | Brain in the decision path? |
| --- | --- | --- |
| `brain` | `log1p` spike counts, ALPN+KC+DN | **yes** |
| `rand_proj` | fixed Gaussian projection of the 283 bits, ReLU | no |
| `bits` | the 283 bits | no |
| `heuristic` | — (`scripts/baseline_heuristic.HeuristicPolicy`) | no |

Robustness: a rejected call (any of the four error names) is logged, the
selection is dropped, and the loop re-reads the game rather than guessing.
But `--max-errors` (default 5) consecutive rejections stop the run, so a
mask/game disagreement cannot spin forever. If `wait_until_stable` times out
still inside an animation state, the loop stops with
`stop_reason="stuck_in_<state>"` instead of burning a poll timeout per
decision.

`auto` tries `brain` first, then `rand_proj`/`bits`, then `heuristic`, and
prints which it got plus `FLY DECIDES` or `brain driven, does NOT decide`. The
brain is driven and logged in every mode, so the spike-rate traces are always
real.

**Resolved.** `outputs/bc3/models/` now holds the v3 glomerular exports, so
`auto` picks the brain readout with no flag needed and announces it:

```
[brain] condition=real n=146271 window=50ms
        populations={'ORN': 2639, 'ALPN': 686, 'KC': 4064, 'MBON': 97, 'DN': 1314}
        feature_version=2 encoding=glomerular32
        (315 bits, 32 to the brain, 32 whole glomeruli, 2075 receptor neurons,
         tuning apl2, 283 bits not sent)
[policy] mode=brain (FLY DECIDES)
[policy] bc3/real_alpn_kc_dn_mlp.npz over ALPN+KC+DN spikes
         (state encoding v2, encoding glomerular32)
```

`FLY DECIDES` is the line to check. `--readout brain` still fails loudly rather
than downgrading silently, so forcing it is a cheap assertion if you are
scripting a demo.

Brain load is ~30 s and ~1.1 GB resident; the per-decision 50 ms window costs
~0.6 s of wall time. A full ante-1 attempt is 30-80 decisions, so budget
2-4 minutes per run at `--pause 1.5`.

## 6. Per-decision log schema

`outputs/realgame/log.jsonl`: one JSON object per line, appended and flushed.
`outputs/realgame/latest.json`: the newest record only, written to a temp file
and `os.replace`d, so a poller never sees a partial object. This is the
subscribe mechanism for the viewer (poll or watch `latest.json`); no websocket,
so no extra dependency and nothing bound to port 8765.
`outputs/realgame/summary.json`: written once when the loop stops.

`population_sizes` in the example below is illustrative; the real numbers come
from the loaded graph (ALPN 686, KC 4064, DN 1314 per
`outputs/bc/brain_features_meta.json`).

```jsonc
{

  "condition": "real",           // or "shuffled"

  "policy_uses_brain": true,     // is the network actually deciding
  "action_index": 70,            // 0..108, indexes env.ACTION_NAMES

  "action_description": "play hand slots [0, 2, 4]",
  "n_legal": 12,                 // popcount of the legality mask

  "relayed_hand_analysis": {
```

### The plasticity mode's records (`--plastic`)

The learning fly decides once per **hand**, not once per action, so its log has
two kinds of record, told apart by `kind`. Everything `overlay.parse_record`
reads (`state.hand`, `state.selected_indices`, `state.blind`,
`relayed_hand_analysis`, `action_name`) is in the same place and the same
shape, so one overlay and one viewer read both kinds of run.

```jsonc
{ "kind": "decision", "hand": 12, "decision": 12,
  "policy_mode": "plastic", "policy_uses_brain": true,
  "action_name": "play",                  // or "discard"
  "relayed_hand_analysis": { /* as above */ },
  "state": { /* as above */ },
  "mb": {                                  // the fly's own output
    "action": "play",
    "approach_hz": 14.545, "avoid_hz": 11.667,   // the two MBON pools
    "raw_drive": 2.878,                          // approach - avoid, Hz
    "play_drive": 0.263,                         // + the calibrated bias
    "p_play": 0.57,                              // THIS hand's probability
    "explored": false,                           // the draw went against it
    "discard_ok": true,
    "bias": -2.616, "temperature": 0.838,        // frozen, from plast2
    "kc_active": 156, "kc_spikes": 163,
    "bucket": "lt1.0", "best_type": "Full House",
    "best_score": 276, "needed": 300, "slots": [0, 1, 2, 3, 6],
    "weights": {                                 // the only mutable state
      "n_synapses": 33496, "n_changed": 2992, "frac_changed": 0.0893,
      "mean_ratio": 0.99598, "min_ratio": 0.95,
      "frac_at_floor": 0.0, "n_at_floor": 0,
      "n_reward_pulses": 12, "n_punish_pulses": 0
    },
    // rolling summaries over the last `rolling_window` hands
    "n_hands": 30, "rolling_window": 50, "reward_rate": 0.4,
    "p_play_rolling": 0.73,                      // NOT the same as `p_play`
    "buckets": {"lt0.25": {"n": 7, "plays": 5, "p_play": 0.7143},
                "ge1.0": {"n": 0, "plays": 0, "p_play": null}},
    "reward_spark": [0, 1, 1, 0], "mean_ratio_spark": [1.0, 0.9997],
    "frac_changed_spark": [0.0, 0.0124]
  }
}

{ "kind": "outcome", "hand": 12, "action": "play",
  "dopamine": "reward",                   // "reward" | "punish" | null
  "outcome": {"chips_gained": 276, "cleared": false, "lost": false,
              "truncated": false, "share": 75.0, "reward": 1, "punish": 0},
  "mb": {"dopamine": "reward", "eta": 0.05, "n_changed": 416,
         "mean_abs_dw": 0.105, "elig_kc": 156,
         "weights": { /* as above */ }, /* + the rolling summaries */ },
  "state": { /* the board the hand was decided on */ },
  "relayed_hand_analysis": { /* what the fly was told about it */ } }
```

Two things worth knowing about the timing. The pulse is delivered against the
Kenyon cells of the window the **decision** was taken in, which by then is one
loop iteration old; that is the coincidence the rule is about, and
`tests/test_realgame_plastic.py` asserts it. And **a discard never earns
dopamine**: crediting a re-deal across a discard is delayed credit assignment
and beyond a fly, so `dopamine` is `null` on every discard outcome.

`p_play` (this hand) and `p_play_rolling` (the last 50 hands) are different
numbers with deliberately different names, because both are merged into the one
`mb` block and a collision silently overwrote one of them during development.
For the same reason an empty bucket's `p_play` is `null`, never `NaN`:
`json.dumps` writes a bare `NaN` for a float nan, which is not JSON and which
the browser's `JSON.parse` rejects.

`--plastic` also writes `weights.npz` (the learned KC → MBON weights, in
`flybalatro.plasticity.WEIGHTS_FORMAT`) into the out dir when the run ends,
including on Ctrl-C.

`summary.json`: `stop_reason` (`ante_cleared`, `game_over_win`,
`game_over_lose`, `max_decisions`, `back_at_menu`, `no_legal_action_in_*`,
`unmappable_state:*`), `decisions`, `wall_seconds`, `condition`,
`policy_mode`, `policy_detail`, `policy_uses_brain`, `blinds_attempted`,
`best_round_score`, `final` (the last state summary). `stop_reason` also covers
`stuck_in_<state>` and `too_many_rejected_calls:<ERROR_NAME>`.

### Two encoding caveats

* In `ROUND_EVAL` and `SHOP` there is no blind with status `CURRENT` or
  `SELECT` (the beaten one is `DEFEATED`, the next is `UPCOMING`), so
  `required_score` is 0 and the score-ratio block lands in bucket 7 rather than
  wherever pylatro would put it. Both are non-decision stages (the only legal
  actions are `cash_out` and the shop set) so it cannot change play, but the
  bits differ from pylatro's there.
* The real game shows the hand sorted (rank-descending by default) while
  pylatro does not. The encoding is positional in both, so this is harmless,
  but slot *i* means a different card in the two engines for the same deal.

## 8. Housekeeping

### Memory: this genuinely matters on this machine

The warning below was written before the real runs and it held up. At the start
of the 2026-09-13 session swap was **15.97 GB of 16.38 GB used, 0.41 GB free**,
with three `flybalatro.viewer.server` instances (ports 8767-8769) each holding
a MaleCNS graph. `play.py` adds another ~1.1 GB resident per run.

**All three viewer servers died during the three real-game runs.** Nothing in
this work signals them (the only `pkill` issued matched
`flybalatro.realgame.play`), and no `memorystatus`/jetsam line was retained in
`log show`, so the cause is not provable after the fact, but memory pressure is
the obvious candidate: the kernel also shrank the swap file from 17.4 GB to
12.3 GB, which is what happens after large processes exit. They were restarted
afterwards; whatever the plastic viewers had learned in RAM since their launch
is gone, and cannot be recovered. The viewers only ever *read* `outputs/plast*`,
so nothing on disk was affected.

If you are going to run the demo and the viewers together, expect to need the
headroom, and start the viewers first: `play.py` fails loudly if it cannot
load, a viewer disappears.


* `pyflakes` was installed into `.venv` to lint the new modules and then
  removed again. If it lingers: `uv pip uninstall pyflakes`.
* **Do not start the demo while `scripts/bc_brain_features.py` is running.**
  `BrainRunner` loads the MaleCNS graph (~1.5 GB) and during this work swap was
  at 12.2 GB of 13.3 GB with 0.1 GB free RAM. Wait for the experiment, or the
  two will fight for memory.

## 9. Unfinished

* **Viewer mirror (`--source realgame`) not done.** The intent was to point the
  port-8767 viewer at the real game so the neuron cloud shows the live
  decisions next to the Balatro window. `latest.json` is the right subscribe
  point and the polling half is trivial, but the viewer's `Simulation.act()`
  owns its own `BalatroEnv` and builds every frame (state panel, substeps,
  decision) from that env. Mirroring means either (a) teaching `Simulation` to
  accept an externally supplied bit vector and state summary instead of
  stepping its env, which touches `Simulation`, `GameLoop` and the frame
  contract the frontend reads, or (b) writing the 315 bits into `latest.json`
  and re-driving the viewer's own brain on them. (b) is the cleaner one and is
  the recommended start: `play.py`'s `DecisionLogger` already has the bits in
  hand at write time. Neither fits in the time this had; nothing was
  half-changed, the viewer is untouched.
* **Ante 2+ never exercised against the real game.** Every run here used
  `--ante-end 1`. Shop handling beyond `next_round` (buying jokers, opening
  packs) has unit tests but no live hours: `plan_action`'s shop branch resolves
  pylatro's per-category slots against BalatroBot's single `shop.cards` array,
  and that mapping has never been exercised on a shop the fly actually wanted
  to buy from; the fly left the shop immediately in all three runs.
* **The 28 s clip is a full-desktop capture.** Window-scoped recording
  (`screencapture -v -l <windowid>`) was not attempted; `GetWindowID` is not
  installed and the API exposes stills only. Crop in post if it matters.
* **`run_lovely_macos.sh` still un-placed**, deliberately; see section 2.
